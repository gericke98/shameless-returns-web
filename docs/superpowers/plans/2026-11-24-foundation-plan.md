## F1: The server boundary is structural, not a convention (closes both security holes)
**Root weakness:** every `"use server"` export is a public endpoint, and each one re-implements "who may touch what".
**Foundation:**
- One `portalAction(handler)` wrapper is the only way to declare a customer action. It resolves the
  session to its order id **on the server** and hands the handler an **order-scoped repository** whose every
  read and write carries `order_id = session.orderId`.
- The handler never receives an order id from the client, and returns a typed `Result`, never `undefined`.
- Internals (carrier booking, repository, Shopify) live in `import "server-only"` modules and cannot be actions.
**Official primitives:** Next server actions + the `server-only` package; rule `server-auth-actions`.
**Check:** a test reads the build's server-reference manifest and fails if any action is not
wrapped; a cross-order write is impossible to express (type error), not just refused.

## F4: The return is an entity with a durable lifecycle (HEAVY)
**Root weakness:** the `orders` row stands in for the return, and fulfilment is one long request.
**Foundation:**
- `return_shipments` keyed by `submission_id`: lane, carrier, locator, label, Amphora return id, state.
  Booking, cancel, tracking and webhooks key on it; Amphora `external_id` = submission id.
- Items always come from the submission's **agreed lines**. Order facts stay on `orders`.
- Confirm (Shopify `returnCreate`), book and email are ledger operations: claim, dispatch with a frozen
  request, read-back evidence, recovery cron.
- The submit action and the Stripe webhook only **record intent and return**. The portal shows the
  shipment's state from the DB, so a dropped connection changes nothing.
- The order snapshot at lookup is one atomic insert with `UNIQUE(order_id, line_item)`.
- A submit command id (generated by the client, stored on `return_submissions`) plus explicit states (awaiting payment /
  processing / completed / failed), so an unknown submit outcome is resolved by reading that command, not
  `/success`'s "any line confirmed" (Santi, 2026-11-24: owned here, not F1).
- The Amphora webhook resolves events through the persisted Amphora return id → shipment, never by `payload.name`
  (`app/api/webhooks/amphora/route.ts:67`, a rule-4 violation found in the F1 review).
- Pinning self-booked tracking and cancelling are transitions of the same shipment row, so a cancel can never cross
  an Amphora pin in flight (the window F1 rev 3 §4 leaves open after its `FOR UPDATE` claim).
**Closes:** wrong warehouse items, second-return reuse, cancel hitting the SHP shadow, paid-but-no-return
on a killed function, and the crash screen after a booked return.
**Decision:** ledger + cron (proven here) vs Vercel Workflow (durable steps; needs F3).
**Check:** on a Neon branch, kill the function after `returnCreate` and recovery completes; a second
return on one order books its own parcel; cancel reaches the real `RET` record.

## F5: One client per external service (HEAVY for Shopify/Stripe)
- Shopify: the settlement transport becomes the only client (one API version, timeout, answer vs
  no-answer, userErrors, `@idempotent` where supported).
- Postmark: one mailer that stores the MessageID and listens to the delivery/bounce webhook.
- Correos/Amphora: timeouts, and a read-back before any revert.
- **All** alerts go through the outbox. For Stripe: superseded sessions are expired, `expires_at` is set,
  and abandonment comes from `checkout.session.expired`, not a clock.

## F6: Money and identity as data (HEAVY)
- Integer-cents line totals and transaction amounts from Shopify. Float text goes.
- Unique constraints instead of application reads: one return line item per accepted submission.
- A partially returnable agreement is refused before `returnCreate`.
- Drain the legacy settlement path and delete `legacyTerms`.

## Order and why
F1 → F2 → F3 → F4 → F5 → F6. F1 first because two holes are live and its foundation is small.
F2 before any HEAVY change so every phase ships through checks. F3 before F4 so the durable
lifecycle is built on the framework it will live on.

## Decisions (Santi, 2026-11-24)
1. **F4 runtime: Vercel Workflow** (`workflow` 5.8.0, GA; `@workflow/next` peer `next >13`). Workflow
   orchestrates the run: confirm, then book, then email. It resumes after a crash or deploy, and retries are typed (`FatalError` / `RetryableError`).
   Postgres stays the record the portal reads (`return_shipments`). Steps are **at-least-once**, so
   every external step is still idempotent on a stable id: Shopify `@idempotent` where supported, otherwise
   read back first; Correos is read back before booking, because its labels can't be cancelled; Amphora uses `external_id` = submission id.
   The settlement ledger stays as it is. Whether it later moves onto Workflow is a separate decision, after F4.
2. **F3 target: Next 16** (`latest` = 16.4.6, stable), React 19, official codemods.
3. **No damage audit.** Instead, every phase ends with the verification below.
