## F1: The server boundary is structural, not a convention (closes both security holes)
**Root weakness:** every `"use server"` export is a public endpoint, and each one re-implements "who may touch what".
**Foundation:**
- One `portalAction(handler)` wrapper is the only way to declare a customer action. It resolves the
  session to its order id **on the server** and hands the handler an **order-scoped repository** whose every
  read and write carries `order_id = session.orderId`.
- The handler never receives an order id from the client, and returns a typed `Result`, never `undefined`.
- Internals (carrier booking, repository, Shopify) live in `import "server-only"` modules and cannot be actions.
**Official primitives:** Next server actions + the `server-only` package; rule `server-auth-actions`.
**Check:** a test reads the build's server-reference manifest and fails if any action is not
wrapped; a cross-order write is impossible to express (type error), not just refused.

## F2: Release pipeline (nothing reaches prod unchecked)
- CI (tsc, lint, single-fork vitest) as a required **Vercel Deployment Check**.
- drizzle-kit: baseline from prod, journal, `migrate` over the direct connection **before promote**.
- Test DBs are built only by replaying migrations, plus a schema↔DB diff check.
- A typed env module, so a missing variable fails the build. Admin tokens are server-only.
- **Neon branch per preview**, and a log drain.
- **Postgres roles as the last boundary** (from F1 §11, Codex review 2026-11-25): a SELECT-only role behind the read
  handle, an `ops_alerts`/`lookup_attempts`-only role, and the writer role behind `writeDb`, each its own connection
  string. Stops hostile in-process code (mutated prepared SQL, namespace-indexed mints) that types cannot.
**Primitives:** Vercel Deployment Checks, drizzle-kit migrator, Neon–Vercel integration.
**Check:** a PR adding a column without a migration fails; the preview DB is not prod's.

## F4: The return is an entity with a durable lifecycle (HEAVY)
**Root weakness:** the `orders` row stands in for the return, and fulfilment is one long request.
**Foundation:**
- `return_shipments` keyed by `submission_id`: lane, carrier, locator, label, Amphora return id, state.
  Booking, cancel, tracking and webhooks key on it; Amphora `external_id` = submission id.
- Items always come from the submission's **agreed lines**. Order facts stay on `orders`.
- Confirm (Shopify `returnCreate`), book and email are ledger operations: claim, dispatch with a frozen
  request, read-back evidence, recovery cron.
- The submit action and the Stripe webhook only **record intent and return**. The portal shows the
  shipment's state from the DB, so a dropped connection changes nothing.
- The order snapshot at lookup is one atomic insert with `UNIQUE(order_id, line_item)`.
- A submit command id (generated by the client, stored on `return_submissions`) plus explicit states (awaiting payment /
  processing / completed / failed), so an unknown submit outcome is resolved by reading that command, not
  `/success`'s "any line confirmed" (Santi, 2026-11-24: owned here, not F1).
- The Amphora webhook resolves events through the persisted Amphora return id → shipment, never by `payload.name`
  (`app/api/webhooks/amphora/route.ts:67`, a rule-4 violation found in the F1 review).
  Seen 2026-11-25: a return pre-registered from a Neon-branch test reached prod's webhook, matched by order id, and wrote
  prod `orders` + emailed. Keyed by shipment, prod would have ignored it. Also: cancel is refused as `carrier-unreadable`
  for ~5 min after a Correos booking (label not yet at Correos); the shipment state should say "booked, not yet scanned".
- Pinning self-booked tracking and cancelling are transitions of the same shipment row, so a cancel can never cross
  an Amphora pin in flight (the window F1 rev 3 §4 leaves open after its `FOR UPDATE` claim).
- A submission is `accepted` only after its Shopify return exists; a failed confirm moves it to `failed`, never leaves it
  `accepted` (#313026, 2026-11-25: three portal retries left three accepted credit submissions for one line).
- Before creating a return, read the line's existing Shopify returns. A customer's own request made outside the portal
  (Shopify Inbox / customer account, status `REQUESTED`) holds the quantity, so `returnCreate` fails "invalid quantity".
  The spec decides whether the portal adopts that request (`returnApproveRequest`) or refuses with a reason; never a retry.
**Closes:** wrong warehouse items, second-return reuse, cancel hitting the SHP shadow, paid-but-no-return
on a killed function, and the crash screen after a booked return.
**Decision:** ledger + cron (proven here) vs Vercel Workflow (durable steps; needs F3).
**Check:** on a Neon branch, kill the function after `returnCreate` and recovery completes; a second
return on one order books its own parcel; cancel reaches the real `RET` record.

## FX: An exchange's replacement is backed by the stock that ships it (HEAVY, found 2026-11-25)
**Root weakness:** the exchange hold is a Shopify draft order with `reserveInventoryUntil`. It only raises Shopify
`committed`; Amphora (the WMS that picks and ships) never sees it, and its inventory sync overwrites Shopify `available`
with its own number. So Amphora keeps selling the held unit. At settlement `orderCreate` runs with
`DECREMENT_IGNORING_POLICY` whenever a hold existed (`lib/settlement/exchangeOrderInput.ts:159`), so a sold-out
replacement still becomes an order nobody can pick. The gate (`lib/autoApproveGate.ts`) never looks at stock.
**Evidence (live reads 2026-11-25 ~23:50Z):** 59 open CAMBIO lines / 46 SKUs; 9 units on 8 SKUs exceed Amphora
`available_quantity`: 20260303 ×2 (#312935, #313090), 20240802 (#313127), 20251904 (#310542), 20252103 (#313008),
20260203 (#312939), 20260901 (#310848), 20261002 (#311618), 20261105 (#313061). Earlier victim #311904. None can settle
on 2026-11-26 07:00Z: every one is pre-warehouse, has no receipt time, or has no Amphora record; the gate opens 2 days
after a receipt time appears.
**Foundation (to design in its own plan, rule 5):** the reservation lives where stock is allocated, or Amphora's stock
is the truth both when an exchange is accepted and at settlement; a replacement that is gone becomes an explicit
customer choice (other size/garment or refund), never a silent stockless order. First question for the plan: can an
order Amphora imports, e.g. a real Shopify order under a fulfillment hold, be counted in Amphora's `reserved_quantity`?
**Research answer (2026-11-26, Amphora Company API spec v1.15.0 + live GETs, Shopify docs via shopify-dev):**
- Tested: Amphora `committed` = units of its orders in PROCESSING/PROCESSING_WAIT/EXCEPTION_CURRIER (184/184 match);
  `reserved` = an order in stock EXCEPTION. A `NEW` imported order and a draft count nowhere. So no Shopify-side object
  (draft hold, held order) reserves at Amphora; it allocates only at preparation.
- Tested: Amphora pushes its `available` into Shopify's Amphora location, overwriting the hold; Shopify `on_hand` then
  invents the held unit. Portal sizes read `ProductVariant.inventoryQuantity` (client-side disable only); the server never
  re-checks stock at submit, payment or settlement.
- Documented, untested: the only Amphora reservation is a B2B `POST /orders` with `flags:["reserve_stock"]`
  (PROCESSING_RESERVED_STOCK). Unknown whether usable for a consumer exchange.
- Tested: 15 of 44 open hold drafts are past `reserveInventoryUntil` yet still make settlement use DECREMENT_IGNORING_POLICY.
- Unknown (only Amphora can answer): connector behaviour for held/unpaid orders; `reserve_stock` for B2C; pushing on_hand.
- Our Shopify token lacks fulfillment-order read scopes.

## F5: One client per external service (HEAVY for Shopify/Stripe)
- Shopify: the settlement transport becomes the only client (one API version, timeout, answer vs
  no-answer, userErrors, `@idempotent` where supported).
- Postmark: one mailer that stores the MessageID and listens to the delivery/bounce webhook.
- Correos/Amphora: timeouts, and a read-back before any revert.
- **All** alerts go through the outbox. For Stripe: superseded sessions are expired, `expires_at` is set,
  and abandonment comes from `checkout.session.expired`, not a clock.

## F6: Money and identity as data (HEAVY)
- Integer-cents line totals and transaction amounts from Shopify. Float text goes.
- Unique constraints instead of application reads: one return line item per accepted submission.
- A partially returnable agreement is refused before `returnCreate`.
- Drain the legacy settlement path and delete `legacyTerms`.

## Order and why
F1 → F4 → F2 → F3 → F5 → F6 (Santi, 2026-11-25: F4 moved up after #313026). F1 first because two holes are live and its foundation is small.
F2 before any HEAVY change so every phase ships through checks. F3 before F4 so the durable
lifecycle is built on the framework it will live on.

## Decisions (Santi, 2026-11-24)
1. **F4 runtime: Vercel Workflow** (`workflow` 5.8.0, GA; `@workflow/next` peer `next >13`). Workflow
   orchestrates the run: confirm, then book, then email. It resumes after a crash or deploy, and retries are typed (`FatalError` / `RetryableError`).
   Postgres stays the record the portal reads (`return_shipments`). Steps are **at-least-once**, so
   every external step is still idempotent on a stable id: Shopify `@idempotent` where supported, otherwise
   read back first; Correos is read back before booking, because its labels can't be cancelled; Amphora uses `external_id` = submission id.
   The settlement ledger stays as it is. Whether it later moves onto Workflow is a separate decision, after F4.
2. **F3 target: Next 16** (`latest` = 16.4.6, stable), React 19, official codemods.
3. **No damage audit.** Instead, every phase ends with the verification below.
